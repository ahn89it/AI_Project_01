### 청킹 (analyzer/indexer.py)
- 대상: CONTROLLER/SERVICE_IMPL 메서드 전부(48개) + Mapper XML SQL 전부(33개) = 총 81청크
- VO/Service 인터페이스/Mapper 인터페이스 메서드는 D4의 layer 필터만으로 자연히 제외됨
  (target-system에 별도 getter/setter가 Controller·ServiceImpl에 없어서 추가 노이즈 필터
  불필요했음)
- 임베딩 텍스트 = "계층/클래스/메서드/URL/주석/관련 테이블" 헤더 + `---` + 실제 코드(또는 SQL) 원문
- **"관련 테이블" 역채움**: graph.db에서 해당 메서드 노드의 하류(outgoing edge)를 전부 따라가
  도달하는 TABLE 노드를 모아서 채움 — `callgraph.get_chain()`이 쓰던 BFS 로직을
  `downstream_subgraph()`로 뽑아내 재사용 (URL 노드든 메서드 노드든 어디서 시작하든 동일하게
  동작). 예: `LoanServiceImpl.insertLoan` 청크에는 TB_MEMBER/TB_LOAN/TB_BOOK/TB_CATEGORY/
  TB_LOAN_HIST가 전부 채워짐
- **node_id 조인키 정확성**: `analyzer/callgraph.py`의 `method_node_id()`/`sql_node_id()`를
  private(`_` 접두사)에서 public으로 바꿔 indexer가 직접 import해서 재사용 — ID 문자열 포맷을
  두 곳에서 따로 구현하면 드리프트로 조인이 깨질 위험이 있어서, 아예 같은 함수를 공유하도록
  만들어 원천 차단
  - 리팩토링 중 사소한 버그 발견: 함수명을 일괄 치환(`_url_node_id`→`url_node_id`)하면서
    기존에 같은 이름을 쓰던 지역변수(`url_node_id = _url_node_id(url)`)와 충돌해
    `UnboundLocalError`가 나는 지점이 있었음 → 지역변수명을 `start_id`로 바꿔 해결. 테스트
    스위트를 다시 돌려서 회귀 없음 확인

### ChromaDB
- `data/chroma/`에 persist, 컬렉션 `code_chunks` 1개, 코사인 유사도(`hnsw:space: cosine`)
- 임베딩은 우리 `EmbeddingService`로 직접 계산해서 `collection.add(embeddings=...)`로 넣음
  (ChromaDB 자동 임베딩 함수를 쓰지 않음 — e5 접두사 규약을 Chroma가 알 리 없으므로)
- 배치 크기 16, 진행 콜백 구조(`progress: Callable[[int,int,str],None]`)로 만들어 D11에서
  UI 진행률 바에 바로 연결 가능. CLI 단독 실행 시엔 tqdm으로 표시

### 검색 (server/services/retriever.py)
- `search(query, top_k=5, layer_filter=None)` — 질의에 `"query: "` 접두사 자동 처리
- 반환: `Hit(node_id, score, metadata, text)`. `score = 1 - cosine_distance`

## 검증 결과 — 한국어 검색 5개 질의 (5/5 전부 통과, 목표 4/5 초과)

| # | 질의 | top-5 1위 결과 (점수) | 판정 |
|---|---|---|---|
| 1 | 도서 대출 처리 절차 | LoanServiceImpl.insertLoan (0.852) | ✅ |
| 2 | 책 반납할 때 연체 처리 | LoanServiceImpl.updateReturn (0.848) | ✅ |
| 3 | 연체 회원 목록 조회 | OverdueController.selectOverdueList (0.843), OverdueServiceImpl.updateRelease 2위(0.842) | ✅ |
| 4 | 회원이 빌릴 수 있는 최대 권수 | **LoanServiceImpl.checkLoanable (0.847)** — 실제로 `LibraryConstants.MAX_LOAN_COUNT` 검증 메서드 그 자체 | ✅ |
| 5 | 도서 등록은 어떻게 하나요 | BookController.insertBook (0.844) | ✅ |

접두사(`passage:`/`query:`)를 처음부터 명시해서 구현했고, 5/5 전부 1차 시도에 통과해 별도
튜닝(헤더 보강/top_k 확대)이 필요 없었다. 특히 4번 질의는 "최대 권수"라는 표현이 코드
어디에도 그대로 나오지 않는데도(`checkLoanable` 메서드명 자체에는 "최대"라는 단어가 없음)
헤더의 "관련 테이블"·주석 정보 없이도 코드 원문 안의 `LibraryConstants.MAX_LOAN_COUNT`,
"최대 대출 권수를 초과했습니다" 메시지가 매칭에 기여한 것으로 보임 — 헤더+원문 구성 전략이
유효했음을 보여주는 사례.

### node_id 조인키 검증 (RAG 전제조건)
5개 질의의 top-5 결과(총 25건, 중복 제외) 전부에 대해 `node_id`로 `graph.db`의 `nodes` 테이블을
직접 조회해서 실제로 존재하는지 확인 — **불일치 0건**. ChromaDB와 graph.db가 같은 ID 체계를
공유하도록 `callgraph.py`의 ID 생성 함수를 그대로 재사용한 설계가 의도대로 작동함.
