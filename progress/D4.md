### analyzer/java_parser.py
- tree-sitter + tree-sitter-java로 AST 파싱
- 클래스 단위: 패키지/클래스명/종류(class·interface·enum)/시작·끝 라인/클래스 어노테이션/
  extends·implements/필드주입(@Autowired, @Resource)/메서드 목록
- 메서드 단위: 이름/반환타입/파라미터/시작·끝 라인/어노테이션/URL(클래스+메서드 @RequestMapping
  계열 조합)/HTTP 메서드/호출식 목록(수신자.메서드명() + 라인)/바로 위 한국어 주석
- eGov 계층 분류(CONTROLLER/SERVICE_INTERFACE/SERVICE_IMPL/MAPPER/VO/ETC)

**개발 중 발견한 버그 2건** (tree-sitter-java 문법 관련, 둘 다 처음엔 조용히 빈 결과를 냄):
1. `modifiers`(어노테이션이 들어있는 노드)가 이 문법 버전에서는 **이름 붙은 필드가 아님** —
   `node.child_by_field_name("modifiers")`가 항상 `None`을 반환해 클래스 어노테이션, 필드주입,
   메서드 어노테이션/URL이 전부 비어 있었음. 실제 target-system을 파싱해보고서야 발견
   (LoanController가 CONTROLLER가 아니라 ETC로, LoanServiceImpl의 injected_fields가 빈 배열로
   나옴). `next(c for c in node.children if c.type == "modifiers")` 위치 기반 조회로 수정
2. `implements` 파싱 시 `super_interfaces` 노드의 자식 중 `implements` 키워드 토큰 자체가
   인터페이스 이름 목록에 섞여 들어감 (`implements: ['implements', 'LoanService']`). `type_list`
   자식만 골라내도록 수정
- 두 버그 모두 "간단한 스니펫으로 스모크 테스트할 땐 안 보이고, 실제 코드 전체를 파싱해야
  드러나는" 유형이라 target-system 실파싱 검증이 왜 완료 기준에 들어가 있는지 체감함

### analyzer/mapper_parser.py
- namespace는 표준 `xml.etree.ElementTree`로 파싱
- SQL 본문(동적 태그 `<if>`/`<foreach>` 포함 원문 보존)과 정확한 라인번호는 ElementTree가
  주지 못해 정규식 기반 텍스트 스캔으로 보완 (MyBatis Mapper XML은 select/insert/update/delete가
  서로 중첩되지 않는다는 전제 위에서 안전)
- 참조 테이블은 `FROM|JOIN|INTO|UPDATE` 뒤 `TB_` 접두사 패턴 정규식으로 추출 (스펙에서 제안한
  방식 그대로 — 80% 정확도로 충분하다는 전제)
