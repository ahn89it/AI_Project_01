# D9 — Text-to-SQL 완성 (★EXAONE 약점 검증일★)

## 목표
"자연어 → SQL 생성 → 안전 검증 → 실행 → 결과"가 안정적으로(3회 중 2회 이상) 동작하는 것 확인.
설계 의도대로 "모델 지능보다 스키마 카탈로그+few-shot 품질"에 집중.

## 사전 점검
D2에서 프로세스로만 띄워둔 MariaDB(3307)가 이전 세션 이후 죽어 있어 재시작
(`mariadbd.exe --defaults-file=...`) — 데이터/ai_reader 계정은 그대로 살아있음을 확인.

## 완료 내역

### server/services/sql_examples.py — few-shot 선택기
- `retriever.search(question, layer_filter="SQL")`로 관련 SQL 청크 검색
- **연체자 4-테이블 JOIN**(`OverdueMapper.selectOverdueList`)을 검색 결과와 무관하게 항상
  예시 풀에 포함 (스펙 지시 그대로)
- MyBatis 동적 태그(`<where>`, `<if>`, `LIMIT #{...}`) 제거/치환해 실행 가능한 형태처럼 정리
  — 그대로 두면 모델이 `<if test=...>` 같은 문법을 흉내내 실행 불가 SQL을 만들 위험
- SQL 문 바로 위 XML 주석을 "용도 설명"으로 재사용(있으면), 없으면 "매퍼클래스.SQL id — 유형
  (테이블: ...)" 형태로 자동 생성

### server/services/sql_guard.py — 안전 검증기
- sqlglot(dialect="mysql")로 파싱: 다중 statement 차단, SELECT 외 전부 차단, `INTO OUTFILE`
  등 위험 패턴 차단, 스키마 카탈로그 대조로 존재하지 않는 테이블 차단, LIMIT 자동추가/100 상한
- 검증 중 발견해 추가한 설계: `GuardError`에 `retryable` 플래그를 둬서, "고쳐서 될 문제"
  (테이블명 오타, 문법 실수)만 재시도하고 "정책 위반"(DELETE 등 파괴적 SQL, 다중 문장)은
  재시도 없이 즉시 거부하도록 구분 (아래 "발견한 문제 2" 참고)

### server/services/prompts.py — TEXT2SQL_SYSTEM_PROMPT
- 스키마 카탈로그(D5 `get_schema_text()`) → 오늘 날짜 주입 → few-shot 4~5개 → 규칙 → 질문
  순서로 프롬프트 구성, temperature 0.1
- `TEXT2SQL_DEMO_TODAY`(config.py, 기본 "2026-08-19")를 프롬프트에 명시 주입 — 실제 시스템
  시계가 아니라 D3 시딩 데이터 기준월(2026-08)에 맞춘 프로젝트 내부 기준일

### server/routers/text2sql.py
- `POST /api/text2sql`: 생성 → 검증 → ai_reader로 실행. 실패 사유를 프롬프트에 덧붙여 1회
  재시도(단, `retryable=False`인 정책 위반은 재시도 생략)
- 실행은 `max_statement_time=10`(초) 세션 설정 + 소켓 타임아웃 이중으로 제한

|---|---|---|---|

| 2 | 가장 많이 대출된 책 10권 | 3/3 동일 SQL, GROUP BY+JOIN+ORDER BY+LIMIT 10 | ✅ |
| 3 | 지금 대출 중인 책 몇 권 | **최초 3/3 "실행 성공"이지만 업무상 오답(40건, 정답 80건)** → 수정 후 재검증 3/3 정답 | ✅ (수정 후) |

### 발견한 문제 1 — "대출 중" 부분 집계 오류 (tip 2가 경고한 함정과는 다른 종류의 함정)
질문 3에서 모델이 매번 `WHERE LOAN_STATUS = '1'`만 세어 40권으로 답했는데, DB를 직접 대조하니
`LOAN_STATUS='3'`(연체중)도 40건 있고 이것도 "아직 반납 안 됨"이라 "대출 중"에 포함되어야
정답(80건)이었음:
```sql
SELECT LOAN_STATUS, RETURN_DATE IS NULL, COUNT(*) FROM TB_LOAN GROUP BY 1,2;
-- 1/미반납 40, 2/반납 170, 3/미반납 40 → 진짜 미반납 80
```
날짜 주입 문제(tip 2)가 아니라 **우리 스키마 고유의 상태값 설계**(연체중도 미반납의 부분집합)를
모델이 스스로 추론하지 못한 경우. 스펙의 1차 대응책("few-shot에 실패 유형과 유사한 예시를
수동으로 추가") 그대로 적용 — `RETURN_DATE IS NULL` 패턴을 보여주는 수동 작성 예시를
`sql_examples.py`에 항상 포함되도록 추가해서 해결. 모델 교체 없이, 스펙이 예고한 순서 그대로
1차 대응만으로 해결됨.

### 발견한 문제 2 — 거부가 "조용히 우회"되던 문제
최초 구현은 가드 실패 시 무조건 1회 재시도했는데, "회원 테이블을 전부 지워줘"에 대해 가드가
DELETE를 막은 뒤 재시도에서 모델이 `WHERE 1=0`처럼 항상 거짓인 SELECT로 "우회"해서
200(빈 결과)이 나옴 — 안전하긴 하지만 "거부됐다"는 게 화면에 안 드러나 시연 자료로 약함.
`GuardError.retryable` 플래그를 추가해 파괴적 SQL/다중문 같은 "정책 위반"은 재시도 없이
즉시 400으로 거부하고, 테이블명 오타 같은 "고칠 수 있는" 문제만 재시도하도록 구분해서 해결.

### 이중 방어 실제 확인 (발표 자료 핵심 소재)
할루시네이션 테이블(TB_SALARY) 질의를 반복하면 두 경로가 확률적으로 나타남: (A) 가드가
테이블 부재를 즉시 차단(400), 또는 (B) 모델이 재시도에서 실재 테이블에 존재하지 않는 컬럼을
지어내 가드는 통과하지만 **읽기전용 계정으로 실제 MariaDB에 실행하는 단계**에서
`Unknown column 'SALARY'`로 최종 차단(200, row_count=0). 어느 경로든 가짜 데이터는 절대
반환되지 않음 — "프롬프트가 뚫려도 SQL 검증이, 검증도 뚫리면 DB 스키마/권한이 막는다"는
이중 방어 구조가 설계대로 작동.
