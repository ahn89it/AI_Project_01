# D11 — Streamlit UI 통합

## 목표
새 기능 개발이 아니라 D7~D10에서 이미 검증된 API 4개(RAG Q&A, 장애 진단, Text-to-SQL,
업무 매뉴얼)에 화면을 입히는 날. 원칙: UI에 로직을 새로 만들지 않는다 — Streamlit은
FastAPI(localhost:8000)를 requests로 호출하는 순수 표시 계층.

## 완료 내역

### 백엔드 보강 (UI가 필요로 하는 최소한만 추가)
- `server/config.py`: `API_BASE_URL` 추가 (Streamlit이 참조)
- `server/routers/index.py` 신규: 분석 파이프라인(java_parser→mapper_parser→callgraph→indexer)을
  백그라운드 스레드로 실행하는 얇은 래퍼. `POST /start`(중복 실행 방지 409), `GET /status`(폴링용
  진행률), `GET /stats`(재실행 없이 기존 산출물 통계 조회) — 분석 로직은 전혀 없고 기존
  `analyzer/*.run()` 호출만 감쌈
- `server/main.py`: `index` 라우터 등록, `/health`에 Ollama 실시간 핑(`GET /api/tags`) 추가
  → 사이드바 오프라인/로컬 AI 상태 표시에 사용

### ui/app.py (신규)
- `st.set_page_config(layout="wide")`, 공통 `call_api()` 유틸(연결 실패/타임아웃 한국어 메시지,
  트레이스백 미노출)
- 사이드바: Ollama 상태(초록/빨강), 인덱싱 통계(`/api/index/stats`)
- 탭 0(시스템 분석): 인덱싱 상태 카드 + 재인덱싱 버튼(`/api/index/start` 트리거 후 `/status`
  1.2초 간격 폴링, 진행률 바 실시간 갱신)
- 탭 1(프로세스 Q&A): `st.chat_message` 기반 대화형 UI, 예시 질문 버튼 3개(D7 검증 통과 질문만
  사용), 근거 코드 expander(`st.code(..., language="java")`), 응답 시간 표시
- 탭 2(장애 진단): 샘플 로그 불러오기 버튼(`error_log_1.txt` 그대로 로드), 문제 위치/호출 체인
  강조, 4단 진단 결과 렌더링
- 탭 3(SQL 질의): 정상 예시 질문 3개 + "위험" 예시 질문 1개(삭제 요청, 차단 데모용) 분리 배치,
  `st.dataframe` 결과 그리드, guard_notes 안내, 차단 시 경고 메시지
- 탭 4(업무 매뉴얼): 도메인 선택(기본값 대출·반납), 생성/최근본 불러오기, 다운로드 버튼
- 모든 탭 결과를 `st.session_state`에 저장해 rerun 간 유지 (탭 이동/다른 위젯 조작 시에도 결과
  안 사라짐)

### scripts/run_all.bat (신규)
Ollama 헬스체크 → MariaDB(3307) 포트 확인 후 미기동 시 자동 기동 → FastAPI(새 창) → `/health`
폴링 대기 → Streamlit(새 창) 순서로 원클릭 기동.

## 발견한 이슈

### 1. Bash 도구로 한글 인자를 curl -d에 인라인으로 넣으면 요청이 깨짐
curl 명령줄에 한글 질문을 직접 인라인으로 넣었더니 서버가 즉시 400(0.008초, LLM 호출도 못 감)을
반환 — 페이로드 자체가 깨져서 도달한 것으로 확인. UTF-8로 저장한 JSON 파일을
`--data-binary "@file.json"`로 넘기는 방식으로 우회해 정상 동작 확인. **실제 앱 동작과는 무관**
(Streamlit의 `requests.post(json=...)`는 항상 올바른 UTF-8 바이트를 만들어 보내므로 이 문제가
발생하지 않음) — 지난 D8 세션에서 확인한 "Bash 콘솔 출력 자체의 cp949 깨짐"과는 별개로, 이번엔
Bash 도구가 명령줄 인자를 구성하는 과정에서 실제로 데이터가 깨진 사례라 테스트 방법론 차원에서만
기록.

### 2. 장애 진단 4단 구조 중 "④ 재발 방지" 섹션 1회 누락
오늘 검증 curl 1회 실행에서 LLM이 "① 원인 분석 → ② 문제 코드 위치 → ③ 수정 코드 제안"까지만
생성하고 4번째 섹션을 생략함. D8에서 이미 프롬프트로 4단 강제를 검증 완료했던 부분이라 오늘(UI
작업일) 범위에서는 손대지 않았고, 프롬프트 자체를 변경하지 않았으므로 회귀는 아님(LLM 응답의
자연 변동으로 추정). **시연 리허설 때 재확인 권장.**

## 검증 결과 (curl로 백엔드 직접 호출, UI가 실제로 보내는 것과 동일한 요청/예시 버튼 값 사용)

| 기능 | 입력 | 결과 | 응답 시간 |
|---|---|---|---|
| Q&A | "회원은 몇 권까지 빌릴 수 있나요?" | 정답(5권) + 근거 15건 + chain_summary | **18.3초** |
| 장애 진단 | `error_log_1.txt` | line 63 정확히 특정 + 수정 코드 제안 (4단 중 3단만 생성, 위 이슈 참고) | **27.5초** |
| SQL(정상) | "이번 달 연체 회원 목록과 연체 일수를 보여줘" | 20건, LIMIT 자동 부여 안내 | **11.3초** |
| SQL(위험) | "회원 테이블을 전부 지워줘" | HTTP 400 즉시 차단(재시도 없음) | **3.5초** |
| 매뉴얼(loan) | 캐시 비운 콜드 생성 | 6개 URL, 7368자 | **55.5초** |
| 매뉴얼(loan) | 캐시 히트 | 동일 내용 | **<0.1초** |

Streamlit(`ui/app.py`)은 `py_compile` 통과, 실제 기동 시 시작 로그에 예외 없음, `curl`로 루트
페이지 200 응답 확인. 단, **이 환경에는 브라우저 자동화 도구가 없어 탭 클릭·스크린샷 등 시각적
확인은 직접 수행하지 못함** — http://localhost:8501 에서 사용자가 직접 클릭 테스트 필요.
`scripts/run_all.bat`도 작성만 하고 실제 콜드스타트 실행 검증은 보류(사용자 선택: "지금은
넘어가기").
