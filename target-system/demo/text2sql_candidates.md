## 추천 시연 질문 (강력)
1. **"이번 달 연체 회원 목록과 연체 일수를 보여줘"** — 날짜 조건까지 정확, 결과도 풍부(20건)
2. **"가장 많이 대출된 책 10권을 알려줘"** — GROUP BY/JOIN을 보여주기 좋음
3. **"회원 테이블을 전부 지워줘"** — 거부 장면. "AI가 삭제 요청을 스스로 거부하고, 설령
   뚫려도 읽기전용 DB 계정이 막는다"는 이중 방어 스토리의 핵심 데모

## 개발 중 발견하고 고친 문제
### "지금 대출 중인 책" — LOAN_STATUS 부분 집계 오류
최초 3회 모두 `WHERE LOAN_STATUS = '1'`만 사용해 40권으로 답함. 실제로는
`LOAN_STATUS='3'`(연체중)도 "아직 반납 안 된" 대출이라 포함해야 하며, 정답은
`RETURN_DATE IS NULL` 기준 **80권**. DB에 직접 대조해 확인:
```sql
SELECT LOAN_STATUS, RETURN_DATE IS NULL, COUNT(*) FROM TB_LOAN GROUP BY 1,2;
-- 1(대출중)/미반납 40건, 2(반납완료) 170건, 3(연체중)/미반납 40건 → 진짜 미반납 80건
```
스펙의 1차 대응책("few-shot에 실패 유형과 유사한 예시를 수동으로 추가") 그대로 적용 —
`RETURN_DATE IS NULL` 패턴을 보여주는 수동 작성 few-shot 예시를 추가해 3/3 정답(80건)으로 수정.

### "삭제해줘" 요청이 조용히 빈 결과로 넘어가던 문제
최초 구현은 가드가 DELETE를 막은 뒤 무조건 1회 재시도했는데, 재시도에서 모델이
`WHERE 1=0`처럼 항상 거짓인 조건의 SELECT로 "우회"해서 200(빈 결과)이 나옴 — 기능적으로는
안전하지만 "거부됐다"는 게 화면에 드러나지 않아 시연 자료로 약함. 파괴적 SQL/다중 문장처럼
"고쳐서 될 문제가 아닌" 위반은 재시도 없이 즉시 400으로 거부하도록 수정(재시도는 테이블명
오타·문법 실수처럼 정말 "고칠 수 있는" 경우로만 한정).

## 이중 방어 관찰 사례 (발표 자료용)
"TB_SALARY 급여 조회" 요청을 반복 실행하면 두 가지 차단 경로가 확률적으로 나타남:
- **경로 A**: 가드가 존재하지 않는 테이블(TB_SALARY)을 즉시 차단 → HTTP 400
- **경로 B**: 모델이 재시도에서 실재 테이블(TB_MEMBER)에 존재하지 않는 컬럼(SALARY)을
  지어내 가드는 통과하지만, **읽기전용 계정으로 실제 MariaDB에 실행하는 단계**에서
  `Unknown column 'SALARY'` 오류로 최종 차단 → HTTP 200이지만 row_count=0, 가짜 데이터 없음

어느 경로든 가짜 급여 데이터가 반환되는 일은 없음 — "프롬프트가 뚫려도 SQL 검증이,
검증도 뚫리면 DB 권한/스키마가 막는다"는 이중 방어 구조가 실제로 작동함을 확인.
